# 01: Pre-Insert Inspection test suite at the pipeline_enqueue_file seam

**What to build:** A passing test suite that proves the four routing behaviors of the Pre-Insert Inspection gate, all exercised through the single ingestion chokepoint (`pipeline_enqueue_file`) without mocking parser internals. The four behaviors: (1) a text-based PDF is inspected, its Markdown is extracted locally by pdf-inspector, and the enqueue call uses `RAW` format with a non-empty `input` string and `parse_engine="pdf_inspector"` (the Local Path, parser bypassed); (2) a scanned PDF is inspected, classified as non-text-based, and the enqueue call uses `PENDING_PARSE` with the originally-resolved engine (the API Path, OCR-capable parser preserved); (3) a non-PDF file (e.g. `.txt` or `.md`) passes through uninspected and enqueues as `PENDING_PARSE` with no inspection-related log; (4) a corrupt or missing PDF fails open — the enqueue call uses `PENDING_PARSE` (fall-through to the parser chain) and a WARNING log containing `fail-open` is emitted. PDF fixtures are generated programmatically at test time (text-based via `reportlab`, which the verification step already proved produces a PDF that pdf-inspector classifies as `text_based` with confidence 1.0; scanned via a minimal image-only or text-operator-free PDF). The test intercepts the call to `apipeline_enqueue_documents` to assert on the enqueue kwargs (docs_format, input, parse_engine). Tests live in `tests/api/routes/` alongside existing document-routes tests and follow the same fixture-and-assertion style.
